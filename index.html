축제 운영과 관람을 함께 다루는 통합 플랫폼입니다. 개발팀장으로 아키텍처 설계를 주도하고, BFF와 마이크로서비스 2개를 개발했으며 6개 레포지토리의 PR 리뷰를 주도했습니다. 게이트 단말과 서버를 모두 구현해, 축제 이틀간 게이트 6대에서 약 15,000건의 태그를 처리했습니다. 운영이 끝난 뒤에는 같은 코드에 부하를 걸어 처리량이 어디에서 막히는지 측정했습니다.

아키텍처

게이트 중단은 입장 대기로 이어지고, 인원 집계는 현장 안전 관리에 필요했습니다. 배포와 장애 범위를 도메인 단위로 나누기 위해 6개 마이크로서비스로 분리했습니다. 아키텍처 설계와 BFF, 서비스 2개 개발을 맡았습니다.

다른 서비스의 데이터는 해당 서비스를 통해 조회하도록 데이터베이스를 서비스별로 나누었습니다. 서비스 간 통신은 gRPC로 통일하고, 개발자들이 함께 사용하는 인터페이스를 .proto에 정의했습니다.

앱이 화면 하나를 그리기 위해 여러 서비스를 호출하지 않도록 BFF에서 응답을 모았습니다. 함께 조회하는 데이터는 GraphQL로 묶고, 단건 처리는 REST로 분리했습니다. 게이트 단말은 BFF를 거치지 않고 입퇴장 서비스에 요청했으며, API 키 헤더로 인증했습니다.

실시간 입퇴장, 인원 관리

게이트 단말이 팔찌를 읽어 서버로 보내면, 서비스는 그 팔찌가 유효한지 확인하고 리더 방향(입장, 퇴장, 재입장)에 따라 상태를 전이시킨 뒤 인원 수를 갱신합니다. 태그 한 건이 지나가는 경로는 아래와 같습니다.

태그 한 건의 처리 경로

인원 수는 Redis 카운터의 원자적 증감으로 집계했습니다. 게이트 여러 대에서 태그가 동시에 들어옵니다. 인원 수를 애플리케이션에서 읽어 더한 뒤 다시 쓰면 같은 시점에 처리되는 태그끼리 서로의 값을 덮어쓸 수 있습니다.

팔찌 유효성과 칩의 마지막 상태는 Redis에 캐시했습니다. 태그 한 건마다 그 팔찌가 유효한 날짜인지 확인해야 하는데, 팔찌 정보는 발급된 뒤 거의 바뀌지 않습니다. 같은 팔찌가 이미 입장했는지도 매번 확인해야 하고, 데이터베이스에서 찾으려면 그 칩의 오늘 이벤트 중 가장 최근 것을 조회해야 합니다. 캐시를 먼저 보고 없으면 데이터베이스를 조회해 채우도록 했고, 상태 키에는 자정 만료를 걸어 날짜가 바뀌면 사라지게 했습니다.

Redis에는 집계 값과 캐시만 두고, 원본은 데이터베이스의 태그 이벤트로 남겼습니다. Redis가 비어도 인원 수를 다시 만들 수 있어야 한다고 생각했습니다. 서비스가 기동할 때 태그 이벤트에서 현재 인원을 다시 세어 카운터를 채우도록 했습니다.

부하 테스트로 찾은 병목과 개선

축제 때는 게이트 6대에서 이틀간 15,000건을 처리했고, 운영 중에는 처리량의 한계가 드러나지 않았습니다. 제가 만든 것이 어디에서 막히는지 알고 싶어서, 운영이 끝난 뒤 같은 코드에 k6로 동시 요청을 5에서 320까지 올리며 태그 처리 API를 측정했습니다. 아래 처리량은 초당 태그 처리 건수, 동시 요청은 k6의 가상 사용자 수입니다.

동시 요청이 10을 넘으면 처리량이 초당 2,930건에서 더 늘지 않았고, 응답 시간만 비례해서 늘어났습니다. 커넥션 풀을 늘리지 않고 코드에서 줄일 수 있는 것을 찾았습니다. 태그 한 건이 데이터베이스를 두 번 오가고 Redis를 네 번 왕복하는데, 그 시간 내내 데이터베이스 커넥션을 잡고 있었습니다.

  • 리더 조회를 메모리에 캐시했습니다. 태그 한 건마다 리더를 데이터베이스에서 조회하고 있었는데, 리더는 6대뿐이고 축제 내내 거의 바뀌지 않습니다. 요청당 데이터베이스 작업이 조회와 적재 두 번에서 적재 한 번으로 줄었습니다. 등록과 상태 변경, 삭제 시점에 캐시를 비우도록 했습니다.
  • 팔찌 유효성과 칩 상태를 한 번에 읽도록 바꾸었습니다. 두 값을 각각 Redis에서 읽고 있어서 왕복이 두 번이었습니다. 키가 둘 다 필요한 입장 경로에서 MGET으로 묶어 한 번에 읽었습니다. 상태를 읽지 않는 퇴장 경로는 그대로 두었습니다.
  • 트랜잭션을 적재 주변으로 좁혔습니다. 태그 처리 메서드 전체에 트랜잭션이 걸려 있어서, 캐시를 조회하고 Redis를 갱신하는 동안에도 데이터베이스 커넥션을 쥐고 있었습니다.
트랜잭션 경계, 태그 처리 전체에서 적재 한 곳으로

게이트 단말의 실시간 처리

축제 직전, 현장과 같은 조건(무선망과 리더 모듈)으로 입장 시나리오를 재현하며 점검하던 중 전원 투입 후 태그 인식까지 지연, 태깅 후 소리와 불빛까지 지연, 태깅 도중 단말이 응답 없이 멈춤 세 가지를 발견했습니다. 구간별로 시간을 로그로 찍어 나눠 보니 원인이 각각 달랐습니다.

  • 부팅 지연은 네트워크 연결이 끝날 때까지 기다린 뒤에야 다음 코드가 실행되는 구조 때문이었습니다. 연결을 기다리지 않고 이벤트로 상태를 받도록 바꿔, 전원 투입 즉시 태그를 읽을 수 있게 했습니다.
  • 피드백 지연은 서버 응답을 받은 다음에 소리와 불빛을 내보내고 있었기 때문입니다. 게이트 앞에 사람이 서 있으니 태그한 즉시 반응을 받는 것이 가장 중요했습니다. 태그를 큐에 넣는 시점에 바로 내보내도록 바꿔, 평균 1~2초이던 피드백 지연을 줄였습니다.
  • 멈춤은 리더 모듈이 약한 신호를 읽는 도중 응답하지 않는 상태에 빠지는 것이었습니다. 없앨 수 없어서 빠르게 감지하는 쪽으로 접근했습니다. 태그 인식과 서버 전송을 각각의 실행 단위로 나누고 사이를 큐로 끊었으며, 인식 단위가 매 주기 하트비트를 남기고 별도 코어의 감시 단위가 1초마다 확인해 2초 이상 끊기면 재시작하도록 했습니다. 멈춤을 최대 3초 안에 감지하고, 감지 후 기기를 재시작하도록 구현했습니다.

신호가 약할 때 들어오는 잘못된 UID는 값의 패턴으로 걸러 서버로 보내지 않았고, HTTPS 연결은 재사용하되 일정 건수마다 끊고 다시 맺어 장시간 운영에서 연결이 고착되는 것을 막았습니다.

배포와 팀 리딩

배포는 GitHub Actions에서 빌드한 이미지를 ECR에 올리고, EC2에서 내려받아 Docker Compose로 교체하는 흐름으로 자동화했습니다. 서비스마다 레포지토리와 워크플로를 따로 두어, 한 서비스를 배포할 때 다른 서비스를 건드리지 않도록 했습니다.

기획, 디자인 파트의 요구사항을 개발자가 바로 착수할 수 있는 형태로 옮기고, 논의와 결정 사항을 Jira 티켓으로 남겼습니다. API 명세는 Swagger로 작성해, 서로의 서비스를 연동할 때 명세만 보고 붙일 수 있게 했습니다. 담당이 나뉘어 있어도 서비스 전체의 코드베이스를 알고 있어야 이후 개발이 수월해진다고 생각하기 때문에, 6개 레포지토리의 PR 리뷰를 주도했습니다.

추론을 별도 서비스로 분리

손바닥 이미지에서 특징 벡터를 뽑는 일과, 사용자와 기관과 디바이스를 관리하고 벡터를 대조하는 일을 한 서비스에 두면 모델이나 전처리를 바꿀 때마다 전체를 다시 배포해야 했습니다. 그래서 추론을 별도 서비스로 분리하고 백엔드는 벡터만 다루도록 했습니다.

기존에는 안드로이드가 화면에 표시된 가이드 사각형 안을 잘라 서버로 보냈습니다. 화면상의 고정 위치를 자르는 것이라 손이 실제로 어디에 어떤 각도로 놓였는지와는 무관했고, 서버는 받은 이미지를 그대로 리사이즈해서 종횡비가 왜곡되었습니다. 회전이나 촬영 거리를 맞추는 단계도 없었습니다.

서버 쪽에 ROI 정렬 단계를 추가했습니다. MediaPipe Hands로 손 랜드마크 21개를 검출하고, 손바닥의 위치와 크기와 방향을 랜드마크에서 계산했습니다.

손가락 뿌리와 손목의 위치로 손바닥 중심을 잡고, 손바닥 너비와 기울기에 맞춰 정사각형 영역을 잘라냈습니다. 손의 위치, 촬영 거리, 회전 각도에 따라 달라지던 입력 영역을 맞추었습니다. 랜드마크 가시성과 유효 픽셀 비율에 따라 이미지를 거부하도록 했으며, 손 검출에 실패하면 컨투어 기반으로 영역을 찾는 대체 경로를 두었습니다.
